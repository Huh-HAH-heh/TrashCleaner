# Проверка текущего TrashCleaner.py

Проверил актуальный `TrashCleaner.py` в `Huh-HAH-heh/TrashCleaner` на `main`.

## Критические ошибки: файл сейчас не запустится

### 1. Не закрыт вызов `add_argument()`

Сейчас:

    parser.add_argument("-r","--recursive",action="store_true",help="рекОбход подпапок"

Не хватает `)`:

    parser.add_argument("-r", "--recursive", action="store_true", help="рекОбход подпапок")

Иначе Python даст `SyntaxError` ещё до запуска программы.

### 2. Нет `:` после `if`

Сейчас:

    if file.stat().st_size == newPath.stat().st_size

Должно быть:

    if file.stat().st_size == newPath.stat().st_size:

Без `:` это второй `SyntaxError`.

### 3. Сломаны отступы около `continue` и `except`

Сейчас структура выглядит примерно так:

    if file.stat().st_size == newPath.stat().st_size:
        print(...)
            continue
        except Exception as e:
            ...

Такой `continue` имеет неверный отступ, а `except` должен относиться к соответствующему `try`. В текущем виде после исправления предыдущей ошибки программа всё равно не распарсится из-за отступов.

Правильная структура должна быть:

    try:
        if file.stat().st_size == newPath.stat().st_size:
            print(...)
            continue
    except Exception as e:
        print(...)
        continue

## Логические проблемы, которые не обязательно дают SyntaxError

### 4. Проверка `item.parent.name != item.suffix...` работает не так, как ты, вероятно, хочешь

Сейчас:

    item.parent.name != item.suffix.replace(".", "").upper()

Например файл:

    test.jpg

в каталоге:

    JPG/

будет пропущен, потому что:

    item.parent.name == "JPG"
    item.suffix... == "JPG"

Но это проверяет только имя непосредственного родителя и при этом предполагает, что имя каталога совпадает с расширением.

У тебя есть гораздо более прямое правило:

    file.parent == newDir

Это проверяет именно то, что файл уже находится в каталоге назначения.

### 5. `if ext in file.parts` слишком широкая проверка

Сейчас:

    if ext in file.parts:
        continue

Это означает: если в любом месте пути встречается часть с именем расширения, файл пропускается.

Например:

    C:\\Work\\JPG\\Project\\photo.png

содержит `JPG` в `file.parts`, поэтому `photo.png` будет пропущен, хотя файл находится не в `PNG`.

Для проверки текущего местоположения лучше:

    if file.parent == newDir:
        continue

### 6. Проверка размера не гарантирует, что это тот же файл

Сейчас при совпадении размеров ты делаешь:

    СКИП

Но два совершенно разных файла могут иметь одинаковый размер.

Например:

    image1.jpg = 100 KB
    image2.jpg = 100 KB

Это не значит, что они одинаковые.

Для cleaner нормальная политика может быть:

    одинаковое имя + существует → создать уникальное имя

а сравнение содержимого/хэшей добавлять только отдельным режимом, если оно реально понадобится.

### 7. При конфликте одинакового размера исходный файл просто остаётся

Сейчас логика:

    целевой файл существует
        ↓
    размеры совпали
        ↓
    SKIP

Это допустимая политика, но она должна быть осознанной. Ты хотел раньше решить коллизии через `_1`, `_2`, ...; текущий код пока этого не делает.

### 8. При конфликте другого размера `newPath` всё равно остаётся занятым

Если целевой файл существует и размеры отличаются, код после блока проверки идёт дальше и вызывает:

    file.rename(newPath)

То есть проблема коллизии не решается. На Windows это, как правило, приведёт к ошибке `FileExistsError`/`OSError` вместо создания `file_1.ext`.

### 9. `except Exception` всё ещё слишком широкий

У тебя:

    except Exception as e:

Для `rename()` и `stat()` разумнее ловить `OSError`.

Широкий `Exception` может скрыть программную ошибку и заставить программу продолжать работу так, будто проблема только в файле.

### 10. `MCount` считает только успешные перемещения

Это нормально, но сейчас отчёта `failed`, `skipped`, `conflicts` нет.

Для личного инструмента полезнее разделить хотя бы:

    Moved
    Skipped
    Failed
    Conflicts

Тогда поведение программы становится понятным после запуска.

Ты уже добавил отдельный режим:

    -r / --recursive

и фактически получил две стратегии:

    glob("*")
    rglob("*")

Это хорошее развитие исходной версии.

Также правильно, что ты сначала формируешь `allFiles`, а потом начинаешь менять файловую систему. Это уменьшает проблемы от изменения дерева во время обхода.

## Что я бы чинил первым

Порядок:

1. Закрыть `add_argument(...)`.
2. Исправить `:`.
3. Исправить отступы `try/except`.
4. Заменить две проверки положения файла на одну: `file.parent == newDir`.
5. Сделать реальное разрешение коллизий: `name.ext → name_1.ext → name_2.ext`.
6. Только после этого улучшать статистику и поведение recursive mode.

Самая важная мысль: **сейчас у тебя проблема не в архитектуре, а в нескольких синтаксических ошибках плюс в двух слишком широких проверках пути**. Саму идею с `Path`, `glob/rglob` и CLI можно спокойно продолжать развивать.
